# AI Agent Guidelines & Repository Architecture (AGENTS.md)

Добро пожаловать! Этот репозиторий спроектирован по высочайшим стандартам программной инженерии: **Clean Hexagonal Architecture (Ports and Adapters)** на бэкенде и **Изолированная модульная компонентная архитектура с SASS-модулями** на фронтенде.

Все ИИ-ассистенты (Gemini, Claude, Cursor, Copilot и др.), работающие с этим репозиторием, **ОБЯЗАНЫ** строго соблюдать изложенные ниже правила. Нарушение архитектурных границ недопустимо.

---

## 1. БЭКЕНД: Архитектура Портов и Адаптеров (Hexagonal)

Бэкенд в папке `/backend` разделен на три изолированных слоя. Главное правило: **Зависимости направлены строго внутрь. Внешние слои знают о внутренних, но внутренние слои никогда не знают о внешних.**

```
   [ Infrastructure Layer (Controllers, Repositories, Prisma) ]
                            │
                            ▼
     [ Application Layer (Use Cases, Ports/Interfaces) ]
                            │
                            ▼
                 [ Domain Layer (Entities) ]
```

### ├── Слой 1: Domain (`/src/domain`)
*   **Что содержит:** Бизнес-сущности (`*.entity.ts`) и чистая бизнес-логика.
*   **ПРАВИЛО ИИ:** **Абсолютная чистота.** В этой папке запрещены любые импорты фреймворков (`@nestjs/...`), ORM (`@prisma/client`), библиотек валидации (`class-validator`) или любых других внешних модулей. Только чистый TypeScript.
*   Сущности инкапсулируют свои бизнес-правила и проверяют внутреннюю согласованность данных.

### ├── Слой 2: Application (`/src/application`)
*   **Что содержит:** Юзкейсы (бизнес-сценарии) и их порты (интерфейсы).
    *   `/ports`: Интерфейсы репозиториев (выходные порты) и интерфейсы юзкейсов (входные порты).
    *   `/use-cases`: Реализация бизнес-сценариев (`*.service.ts`).
*   **ПРАВИЛО ИИ:**
    *   Реализации юзкейсов должны зависеть **только** от бизнес-сущностей (`domain`) и интерфейсов портов (`ports`).
    *   **Запрещено** внедрять конкретные реализации (например, импортировать `PrismaWorkLogRepository`). Внедрение зависимостей должно происходить строго через конструктор с использованием типов интерфейсов-портов (инъекция токенов).

### ├── Слой 3: Infrastructure (`/src/infrastructure`)
Адаптеры, которые связывают ядро приложения с внешним миром (БД, Сеть).

*   **HTTP-Адаптеры (`/controllers`):**
    *   Принимают HTTP-запросы.
    *   Валидируют входные данные с помощью строго типизированных DTO (`class-validator`, `class-transformer`).
    *   Вызывают интерфейсы юзкейсов.
    *   Мапят доменные сущности в выходные JSON DTO.
*   **Persistence-Адаптеры (`/repositories`):**
    *   Реализуют интерфейсы выходных портов (`*Repository.interface.ts`).
    *   Используют `PrismaService` для прямого взаимодействия с СУБД.
    *   **ОБЯЗАТЕЛЬНО:** Используют Мапперы (`/mappers`) для преобразования строк БД/моделей Prisma в чистые сущности Domain (`*.entity.ts`) на выходе, и обратно на входе. Слой базы данных никогда не должен «просачиваться» в слой юзкейсов.
*   **DI Сборка (`/nest`):**
    *   NestJS Модули связывают интерфейсы портов (`application/ports`) с их инфраструктурными реализациями.
    *   Пример биндинга:
        ```typescript
        {
          provide: 'WorkLogRepositoryPort',
          useClass: PrismaWorkLogRepository,
        }
        ```

## 2. ФРОНТЕНД: Модульная компонентная архитектура с SASS

Фронтенд в папке `/frontend` спроектирован по модульному компонентному принципу, исключающему конфликты стилей и накопление технического долга.

### Глобальный UI Kit (`/src/components`)
*   Содержит атомарные, глупые (presentation) компоненты общего назначения (`Button`, `Input`, `Select`, `Modal`, `Loader`).
*   Каждый компонент лежит в **собственной папке** с файлом логики (`Component.tsx`) и изолированным файлом стилей (`Component.module.scss`).

### Бизнес-фичи (`/src/features`)
*   Содержит изолированные доменные фичи (например, `/work-logs`).
*   Внутри фичи находятся:
    *   `/components`: Сложные компоненты, относящиеся только к этой фиче (`WorkLogTable`, `WorkLogForm`).
    *   `/hooks`: Локальные кастомные хуки для управления сложным состоянием фичи (`useWorkLogFilters`).
*   **ПРАВИЛО ИИ:** Запрещен экспорт внутренних вспомогательных компонентов за пределы папки фичи. Доступ должен предоставляться только через индексный файл, если необходимо.

### Слой стилей (`/src/styles`)
*   Использование **SASS (SCSS)** обязательно.
*   `_variables.scss` содержит HSL дизайн-токены (цвета, радиусы, шрифты) для темной премиальной темы.
*   Используйте CSS-модули (`*.module.scss`) для предотвращения утечки стилей в глобальную область.
*   Глобальные стили подключаются только в `global.scss`.

### Слой запросов (`/src/api`)
*   Работа с сетью ведется через **TanStack Query (React Query)** и **Axios**.
*   **ПРАВИЛО ИИ:** Запрещено вызывать `fetch` или `axios` напрямую внутри React-компонентов. Все запросы данных (`queries`) и изменения данных (`mutations`) должны быть инкапсулированы в кастомные хуки в `/api/workLogsApi.ts`.
*   При успешном выполнении мутаций (создание, удаление, обновление) обязательно инвалидируйте соответствующий кэш (`queryClient.invalidateQueries`) для мгновенного обновления интерфейса.

## 3. ЗОЛОТЫЕ ПРАВИЛА ДЛЯ ИИ-ПОМОЩНИКОВ

1.  **Strict TypeScript:** Никаких `any`. Все типы, интерфейсы, DTO, сущности и возвращаемые значения функций должны быть явно типизированы.
2.  **Запрет на God-файлы:** Длина файла не должна превышать 250 строк. Если файл становится больше — выносите вспомогательные функции, мапперы, хуки или стили в отдельные файлы.
3.  **Принцип наименьшего удивления (POLA):** Код должен быть читаемым. Используйте понятные, развернутые имена переменных и функций (`createWorkLogUseCase` вместо `cwlUC`).
4.  **Безопасность данных:** Никогда не пишите запросы к БД напрямую в обход Prisma ORM, чтобы избежать SQL-инъекций. Всегда используйте валидационные DTO на входе в контроллеры.
5.  **Премиальный UX/UI:**
    *   При обновлении интерфейса помните: дизайн должен быть эстетически великолепным (Glassmorphism, HSL палитры, темная тема, тонкие светящиеся границы).
    *   Любое длительное действие должно сопровождаться **Skeleton Loader** или микроанимацией загрузки.
    *   Любое деструктивное действие (удаление) должно иметь плавную анимацию исчезновения элемента.

## 4. ПРАВИЛА СОЗДАНИЯ КОММИТОВ (COMMIT GUIDELINES)

Все коммиты должны создаваться **последовательно, маленькими логическими батчами (порциями)**. Запрещено коммитить все файлы проекта одной огромной кучей.

### Формат имени коммита:
Имя коммита должно начинаться с типа изменения (области) и двоеточия, после чего пишется краткое описание на английском языке:
`<type>(<scope>): <description>` или `<type>: <description>`

**Основные типы коммитов:**
*   `feat` — добавление новой функциональности (например: `feat(backend): add work log create endpoint`).
*   `fix` — исправление багов (например: `fix(frontend): resolve path resolution error`).
*   `chore` — настройка конфигураций, сборщиков, зависимостей (например: `chore: configure gitignore`).
*   `docs` — обновление документации (например: `docs: update readme`).

### Перечисление нескольких изменений:
Если коммит содержит несколько изменений, их описание оформляется в виде маркированного списка, отделенного от первой строки **пустой строкой**:

```text
feat:

- add first change;
- add second change.
```

**Примеры корректных коммитов:**
```text
feat: add something
```
```text
feat(backend): implement Domain entities for WorkType and WorkLog
```
```text
fix:

- fix border-radius styles in button;
- resolve legacy SASS deprecation warnings.
```
